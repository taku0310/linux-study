## 0. 全体像 — なぜプロセスとスレッドを学ぶのか

組み込みLinuxの実機では、1つの基板の上で
「センサ読み取り」「制御演算」「通信」「ログ書き込み」といった
複数の仕事が**同時に**動きます。これを実現する単位が
**プロセス**と**スレッド**です。

- **プロセスを分ける** → 障害の分離。カメラ処理が落ちても制御ループは生きる。
- **スレッドを分ける** → 低レイテンシな並行処理。同じデータを共有しつつ軽量に切替。

ROS2 のノードは「プロセス」、その内部のコールバック実行は「スレッド(executor)」
で動きます。デバイスドライバも、割り込みハンドラとカーネルスレッドが
協調して動きます。つまり**プロセス/スレッドの理解は、この講座の全テーマの土台**です。

```
                 ┌────────────────────────── ハードウェア ──────────────────────────┐
                 │  CPU core0   CPU core1   CPU core2   CPU core3   ... メモリ ... I/O │
                 └───────────────▲──────────────────────────────────────────────────┘
                                 │ スケジューラ(CFS/EEVDF)が「次に誰を走らせるか」決定
   ┌─────────────────────────────┼──────────────────────────────────────────────┐
   │ プロセスA (制御)             │        プロセスB (通信)      プロセスC (ログ)     │
   │  ├ thread0(main)            │         ├ thread0           ├ thread0          │
   │  ├ thread1(制御ループ)  ← 各スレッドが「実行可能タスク」としてCPUを奪い合う      │
   │  └ thread2(監視)            │         └ thread1                              │
   └────────────────────────────────────────────────────────────────────────────┘
```

# 第1部 概念編

## ① プロセスとは何か

### なぜこの知識が必要か
「実行中のプログラム」を OS がどう管理しているかを知らないと、
メモリリーク・ゾンビ・権限の問題を追えません。組み込みでは
リソースが限られるため、プロセスの実体を理解することが必須です。

### OS内部で何が起きているか
プロセスとは、**実行中のプログラムのインスタンス**であり、Linux カーネル内では
`struct task_struct`(`include/linux/sched.h`)という構造体で表現されます。
1つの `task_struct` が持つ主な情報:

- **PID / TGID**: 識別子
- **メモリ管理情報** `struct mm_struct`: 仮想アドレス空間、ページテーブル
- **ファイルディスクリプタ表** `struct files_struct`: 開いているファイル
- **シグナルハンドラ** `struct signal_struct`
- **スケジューリング情報** (優先度・実行時間・所属 CPU)
- **資格情報(credentials)**: UID/GID、capabilities

プロセスは仮想アドレス空間を1つ持ち、それは MMU(メモリ管理ユニット)によって
物理メモリへ変換されます。**各プロセスは「自分だけが全メモリを持っている」
かのように振る舞える**——これが仮想記憶の恩恵です。

### イメージ図
```
プロセス (task_struct + mm_struct)
┌───────────────────────────── 仮想アドレス空間 ─────────────────────────────┐
│ 0xFFFF... ┌──────────────┐ ← カーネル空間 (ユーザからは触れない)             │
│           ├──────────────┤                                                  │
│           │   stack      │ ↓ 関数呼び出しで伸びる (自動変数・戻り番地)          │
│           │     ...      │                                                  │
│           │   (空き)     │                                                  │
│           │     ...      │                                                  │
│           │   heap       │ ↑ malloc で伸びる                                 │
│           ├──────────────┤                                                  │
│           │   .bss       │ 未初期化グローバル (0 埋め)                          │
│           │   .data      │ 初期化済みグローバル                                │
│           │   .text      │ 機械語コード (読み取り+実行、共有可能)               │
│ 0x0000... └──────────────┘                                                  │
└────────────────────────────────────────────────────────────────────────────┘
```

### 用語
| 用語 | 意味 |
|------|------|
| task_struct | カーネルがプロセス/スレッドを管理する構造体。「タスク」の実体 |
| mm_struct | 1つのアドレス空間を表す構造体。プロセスに1つ、スレッド間で共有 |
| 仮想アドレス空間 | プロセスから見える連続したメモリ。MMUが物理に変換 |
| PCB | Process Control Block。一般OS用語で、Linuxでは task_struct が相当 |

### サンプル / 実行
`app/01_process_basic.c` — 自分の PID/PPID/TID を表示するだけの最小プロセス。

```bash
make run-01_process_basic      # あるいは ./build/01_process_basic
```
実行結果:
```
[main          ] PID=1234 PPID=1000 TID=1234
```
シングルスレッドなので **PID == TID**。sleep 中に別ターミナルで
`ps -o pid,ppid,stat,cmd -p 1234` を叩くと状態が見えます。

## ② スレッドとは何か

### なぜこの知識が必要か
プロセスをまるごと複製(fork)するのは重い。同じデータを共有して
軽く並行実行したい——それがスレッドです。制御ループと監視を
別スレッドにする、といった設計は組み込みで日常的に登場します。

### OS内部で何が起きているか
**Linux にはカーネルレベルで「スレッド専用の型」は存在しません。**
スレッドも `task_struct` で表現され、プロセスと同じ「タスク」です。
違いは **何を共有するか** だけ:

- `fork()` → `clone()` を「ほぼ何も共有しない」フラグで呼ぶ → 新プロセス
- `pthread_create()` → `clone()` を **`CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD ...`** で呼ぶ → 同じ `mm_struct`・FD表・シグナル設定を**共有**する新タスク

つまりスレッドとは「同じアドレス空間を共有する軽量タスク」です。
Linux ではこれを **LWP (Light Weight Process)** とも呼びます。
同一プロセスの全スレッドは **同じ TGID (=ユーザ空間のPID)** を持ち、
**それぞれ固有の PID (=ユーザ空間のTID)** を持ちます。

### イメージ図
```
プロセス (TGID=1234) ── mm_struct を全スレッドで共有
┌──────────────────────────────────────────────┐
│ .text .data .bss  heap    ← 全スレッド共有       │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐          │
│ │ thread0  │ │ thread1  │ │ thread2  │          │
│ │ TID=1234 │ │ TID=1235 │ │ TID=1236 │          │
│ │ 専用stack│ │ 専用stack│ │ 専用stack│  ← stack だけ各自 │
│ │ 専用レジスタ(PC/SP)     ...          │          │
│ └──────────┘ └──────────┘ └──────────┘          │
└──────────────────────────────────────────────┘
```
**共有するもの**: コード、グローバル変数、ヒープ、FD、シグナルハンドラ
**各スレッド固有**: スタック、レジスタ(PC/SP)、`errno`、TLS(Thread Local Storage)

### サンプル
`app/07_pthread_basic.c` — 3スレッドが同じ `g_shared` を触り、
PID共通・TID別を確認。`app/09_pid_tid.c` — getpid/gettid の差を厳密に確認。

## ③ プロセスとスレッドの違い

| 観点 | プロセス | スレッド |
|------|----------|----------|
| アドレス空間 | 独立(各自 mm_struct) | 共有(同一 mm_struct) |
| 生成コスト | 重い(ページテーブル複製=COW) | 軽い(共有するだけ) |
| 通信手段 | パイプ/共有メモリ/ソケット/シグナル (IPC) | グローバル変数を直接読み書き |
| 障害の波及 | 1つ落ちても他は生存(分離) | 1つが不正メモリアクセス→プロセスごとクラッシュ |
| コンテキストスイッチ | 重い(ページテーブル切替=TLBフラッシュ) | 軽い(アドレス空間そのまま) |
| 識別子 | PID (=TGID) | TID (=カーネルpid)、PIDは共通 |
| 生成API | `fork()`/`posix_spawn()` | `pthread_create()` |

**設計指針(組み込み観点)**:
- **堅牢性・隔離を優先** → プロセス分割(片方が落ちても制御は継続)
- **低レイテンシ・密なデータ共有を優先** → スレッド(共有メモリで即座に連携)
- 実務では両者を併用: プロセスで機能ブロックを分け、各プロセス内でスレッド並行。

## ④ メモリ空間の違い

### OS内部で何が起きているか
`fork()` 直後、親子は**同じ物理ページ**を指すページテーブルを持ちますが、
全ページに **COW (Copy-On-Write)** の印(書込禁止)が付きます。
どちらかが書き込もうとするとページフォルトが発生し、カーネルが
そのページだけ物理的に複製して各自に割り当てます。
だから「フォークは速いのに独立している」を両立できます。

スレッドは `CLONE_VM` により **同じ `mm_struct` を共有**するので、
一方の書き込みが即座に他方から見えます。これが強力さと危険さの源です。

### サンプルで体感
```bash
# プロセス: 変数を書き換えても互いに影響しない (COWで独立)
make run-02_fork
#   parent: value=1100   child: value=101   ← 別々

# スレッド: 同じグローバルを共有 → 排他しないと壊れる
make race      # mutexなし: counter が期待値8000000より小さくなる (DATA RACE)
make mutex     # mutexあり: 常に8000000で正しい
```
`make race` の実行例(-O0でビルド、値は毎回変わる):
```
[race  ] counter=2932720 expected=8000000  DATA RACE (差=5067280)
```
`counter++` は「読む→+1→書く」の3ステップ(非アトミック)。
複数スレッドが同時にこれをやると更新が失われます。
**共有メモリには必ず排他(mutex/atomic)を**——これがスレッドの鉄則。

## ⑫ PID・TID(ここで整理しておく)

用語がねじれているので、カーネル視点で正確に押さえます。

| ユーザ空間の呼び方 | 取得API | カーネル内部の呼び方 | 説明 |
|--------------------|---------|----------------------|------|
| **PID** (プロセスID) | `getpid()` | **TGID** (thread group id) | プロセス全体の代表ID。全スレッド共通 |
| **TID** (スレッドID) | `gettid()` | **pid** (task の id) | 個々のタスク(スレッド)の識別子 |

- シングルスレッドのプロセスは `getpid() == gettid()`(TGID と代表スレッドの pid が一致)。
- スレッドを作ると、新スレッドの `gettid()` は別の値、`getpid()` は同じ。
- `/proc/<PID>/task/` 以下に、そのプロセスの全スレッド(TID)がディレクトリとして並ぶ。

```bash
make run-09_pid_tid &      # バックグラウンド実行
PID=$!
ps -T -p $PID              # SPID 列が各スレッドの TID
ls /proc/$PID/task/        # TID がディレクトリとして見える
```
実行例:
```
  PID  SPID TTY          TIME CMD
 4646  4646 ?        00:00:00 09_pid_tid   ← main (PID==TID)
 4646  4648 ?        00:00:00 09_pid_tid   ← worker LWP
 4646  4649 ?        00:00:00 09_pid_tid
```

# 第2部 プロセス系システムコール

## ⑤ fork()

### OS内部で何が起きているか
`fork()` はライブラリ経由で `clone()` システムコールを呼び、カーネルは
呼び出し元の `task_struct` を複製します。
mm_struct のページは COW 共有、FD 表も複製(FD自体は共有)されます。
**1回の呼び出しで親子2つの実行フローに分岐**し、それぞれで `fork()` が return します。

- 親への戻り値: 子の PID(>0)
- 子への戻り値: 0
- 失敗: -1(`errno` に ENOMEM / EAGAIN など)

### 用語
| 用語 | 意味 |
|------|------|
| COW | Copy-On-Write。書き込むまで物理ページを共有し、書込時に複製 |
| clone() | Linux固有のタスク生成システムコール。fork/thread の実体 |
| fork bomb | 無限に fork してシステムを枯渇させる事故/攻撃。`ulimit -u` で防御 |

### サンプル / 実行結果の解説
`app/02_fork.c`:
```bash
make run-02_fork
```
```
before fork: value=100
[parent-pre    ] PID=4158 PPID=3802 TID=4158
[parent        ] PID=4158 PPID=3802 TID=4158
[child         ] PID=4159 PPID=4158 TID=4159     ← 子のPPIDは親のPID
  parent: value=1100                              ← 親は +1000
  child : value=101                               ← 子は +1  (独立)
child PID=4159 exited normally, status=0          ← 親が wait で回収
```
着目点:
- 子の **PPID(4158) = 親の PID**。親子関係がIDで確認できる。
- `value` が親子で別々 → COW によりメモリが独立している。
- `fork` の前に `fflush(stdout)` しないと、バッファ内の未出力文字列が
  **親子両方で複製されて二重出力**される(よくある罠、後述)。

### よくある間違い
- **戻り値を見ずに処理** → 親子両方が同じコードを実行してしまう。
- **wait 忘れ** → 子がゾンビ化(⑬)。
- **fork 前の未flushバッファ** → 出力が二重になる。`printf` 後 `fflush` を。

## ⑥ exec()

### なぜこの知識が必要か
「別のプログラムを起動する」= シェルがコマンドを実行する仕組みそのもの。
`system()` や `posix_spawn()` の内部もこれです。組み込みでは
自作アプリから外部ツール(`i2cdetect`, `ffmpeg` 等)を起動する場面で使います。

### OS内部で何が起きているか
`exec` 系(`execve` が本体)は**新しいプロセスを作りません**。
呼び出したプロセスの**アドレス空間を、指定した実行ファイルの内容で丸ごと置換**します。
- `.text`/`.data`/`.bss`/heap/stack は破棄され、新プログラムのものに差し替え。
- **PID は変わらない**(同じ task_struct のまま中身が入れ替わる)。
- 開いていた FD は原則引き継がれる(`FD_CLOEXEC` が付いた FD は閉じられる)。
- 成功すると**元のコードには二度と戻らない**。戻ってきたら失敗。

### 定石: fork + exec
```
親 ──fork()──▶ 子(親のコピー)
                 └─exec("ls")──▶ 子の中身が ls に置換され、ls が走る
親 ──wait()──▶ 子(ls)の終了を回収
```

### サンプル / 実行結果
`app/03_exec.c`:
```bash
make run-03_exec
```
```
[parent            ] PID=4160 ...
[child-before-exec ] PID=4161 ...   ← exec 前は自作コード
total 28                             ← ここから先は ls の出力(execで化けた)
-rw-r--r-- 1 root root 2028 ... Makefile
...
=== 親は生き残っている ===          ← 親は無傷
```
`child-before-exec` の後、コードは `ls` に置き換わり、
「exec の次の行(perror)」には到達していない = exec 成功の証拠。

### 用語
| API | 特徴 |
|-----|------|
| `execlp` | 引数をリストで渡す(l)、PATH検索(p)。`execlp("ls","ls","-l",NULL)` |
| `execvp` | 引数を配列で渡す(v)、PATH検索(p)。動的な引数に便利 |
| `execve` | 本体のシステムコール。環境変数も明示的に渡す |

### よくある間違い
- 引数リストの**末尾 `(char*)NULL` 忘れ** → 未定義動作。
- `exec` 後にコードを書いて「戻ってくる前提」で処理 → 成功時は戻らない。
- exec失敗時の終了コードを 0 にしてしまう → 慣習は 126/127。

## ⑦ wait()

### なぜこの知識が必要か
子の**終了を回収**しないとゾンビが溜まり、PIDテーブルを圧迫します。
長時間動く組み込みデーモンでは致命的。終了コードで子の成否を
判定するのも wait の役割です。

### OS内部で何が起きているか
子が `exit` すると、カーネルは子の資源(メモリ・FD)を解放しますが、
**終了ステータスだけは `task_struct` に残して親の回収を待ちます**。
この状態が **ゾンビ (EXIT_ZOMBIE)**。親が `wait()`/`waitpid()` を呼ぶと、
カーネルはステータスを親に渡し、残った `task_struct` を解放します。
子が終了すると親に **`SIGCHLD`** が送られるので、それを契機に回収するのが定石。

### ステータス判定マクロ
| マクロ | 意味 |
|--------|------|
| `WIFEXITED(s)` | 正常終了(exit/return)なら真 |
| `WEXITSTATUS(s)` | その終了コード(0-255) |
| `WIFSIGNALED(s)` | シグナルで殺されたら真 |
| `WTERMSIG(s)` | 致命シグナル番号 |
| `waitpid(pid, &s, WNOHANG)` | ブロックせず即戻る(ポーリング用) |

### サンプル / 実行結果
`app/04_wait.c` — 3子を別々の終了コードで終わらせ、順に回収:
```
  child #0 (PID=4163) working 1 s ...
  child #1 (PID=4164) working 2 s ...
  child #2 (PID=4165) working 3 s ...
child PID=4163 exited normally, status=10    ← 早く終わった順に返る
child PID=4164 exited normally, status=11
child PID=4165 exited normally, status=12
```
`wait()` は**終わった子から順に**返る点に注目。特定の子を待つなら `waitpid`。

## ⑬ ゾンビプロセス

### 何が起きているか
子が終了 → 親が未回収 → 子は `Z (defunct)` 状態で `task_struct` だけ残る。
ゾンビは**メモリもCPUも使わない**が、**PID を1つ占有**し続けます。
大量発生すると PID 枯渇(`kernel.pid_max` 到達)で新規プロセスが作れなくなる。

### 観察
`app/05_zombie.c`(親がわざと wait しない):
```bash
./build/05_zombie &        # バックグラウンドで起動
PID=$!
ps -o pid,ppid,stat,cmd --ppid $PID
```
```
  PID  PPID STAT CMD
 5403  5401 Z    [05_zombie] <defunct>     ← STAT=Z, CMD=<defunct>
```
`STAT` 列の `Z` と `<defunct>` がゾンビの目印。

### 対処
1. 親が必ず `wait()`/`waitpid()` する。
2. `SIGCHLD` ハンドラで回収する(イベント駆動デーモンの定石):
   ```c
   signal(SIGCHLD, SIG_IGN);  // 子を自動回収させる簡易法(POSIX保証あり)
   // または SIGCHLD ハンドラ内で while(waitpid(-1,&s,WNOHANG)>0);
   ```
3. **親を終了させる** → ゾンビは init/systemd(PID1)に引き取られ、
   PID1 が回収してくれる(だからプログラム終了時にゾンビは消える)。

### よくある間違い
- SIGCHLDハンドラで `wait` を**1回だけ**呼ぶ → 同時に複数子が死ぬと取りこぼす。
  必ず `while(waitpid(-1,&s,WNOHANG)>0){}` でループ回収する。

## ⑭ 孤児プロセス

### ゾンビとの違い
| | ゾンビ | 孤児(orphan) |
|---|--------|--------------|
| 状態 | 終了済み、未回収 | **生きて動いている** |
| 原因 | 子が先に死に、親が wait しない | **親が先に死に、子が生き残る** |
| 問題か | PID を無駄に占有(問題) | 通常は問題なし。新しい親が最後に回収 |
| 引取り先 | (親が死ねば)PID1 が回収 | 即座に PID1 または subreaper に再親付け |

### 何が起きているか
親が終了すると、生き残った子の親は失われます。カーネルは孤児を
**即座に再親付け(re-parenting)** します。引き取り手は:
1. `prctl(PR_SET_CHILD_SUBREAPER)` を設定した最寄りの祖先(systemd の
   ユーザセッション等がこれ)、なければ
2. **PID 1(init/systemd)**。

### 観察
`app/06_orphan.c`(親が即終了、子が生き残る):
```
parent PID=6142 exits immediately, leaving child orphaned
  child PID=6143, PPID=6142 (最初の親)
  child PID=6143, PPID=1   (親が死んだ後 → 再親付け)   ← PPIDが1に変化!
```
`PPID` が `6142 → 1` に変わった = 再親付けの瞬間。

### 実務での意味
デーモン化(daemonize)は**わざと孤児を作る**技術です。
`fork()` して親を終了させ、子を systemd/init 配下にぶら下げることで、
起動元のシェルから切り離された常駐プロセスを作ります
(現代は systemd unit に任せるのが主流だが、原理は同じ)。

# 第3部 スレッド系API

## ⑧ pthread_create()

### OS内部で何が起きているか
`pthread_create()` は内部で `clone()` を **`CLONE_VM|CLONE_FS|CLONE_FILES|
CLONE_SIGHAND|CLONE_THREAD|CLONE_SETTLS|...`** を付けて呼びます。
新タスクは呼び出し元と同じ `mm_struct` を共有し、**スタックだけ新規に確保**
(デフォルト約8MB、`ulimit -s`)されます。生成された瞬間から
スケジューラの実行キューに乗り、独立にCPUを奪い合います。

### 重要な作法
- pthread 系関数は **errno を使わず、戻り値でエラーコードを返す**
  (0=成功)。`if (rc != 0) strerror(rc);` で扱う。
- 引数は `void*` 1個。複数渡すなら構造体のポインタを渡す。
- **ループ変数のアドレスを直接渡さない**(全スレッドが同じ変数を見て競合)。

### サンプル
`app/07_pthread_basic.c`:
```
[main   ] PID=4166 ... TID=4166
[worker ] PID=4166 ... TID=4167   ← PID共通、TID別
[worker ] PID=4166 ... TID=4168
final g_shared = 3 (期待値 3)
```

---

## ⑨ pthread_join()

### 役割
- スレッドの**終了を待つ**(ブロック)。
- スレッドの**戻り値を回収**する(`void**` で受ける)。
- スレッドが使っていたリソース(スタック等)を**解放**する。

**join しないとどうなるか**: `pthread_detach()` していないスレッドは、
終了しても資源が残り続けます(スレッド版のゾンビに相当)。
待つ必要がない「撃ちっぱなし」スレッドは `pthread_detach()` するか、
生成時に detached 属性を付けます。

```c
pthread_join(th, &ret);        // 終了待ち + 戻り値回収
// または
pthread_detach(th);            // 待たずに自動解放させる
```

### プロセスとの対比
| | プロセス | スレッド |
|---|---------|----------|
| 生成 | `fork()` | `pthread_create()` |
| 終了待ち・回収 | `wait()`/`waitpid()` | `pthread_join()` |
| 未回収の残骸 | ゾンビプロセス | 未joinのスレッド資源 |
| 撃ちっぱなし化 | (親を終了→PID1へ) | `pthread_detach()` |

### スレッド同期の道具(共有メモリの必需品)
| 道具 | 用途 |
|------|------|
| `pthread_mutex_t` | 相互排他。臨界区間を1スレッドだけに |
| `pthread_cond_t` | 条件変数。「データが来るまで待つ」通知 |
| `pthread_rwlock_t` | 読み手多数/書き手排他 |
| `atomic_int` (C11) | ロックなしのアトミック変数。カウンタ等に |
| `sem_t` | セマフォ。資源数を数える |

`make race` / `make mutex` でmutexの有無による違いを体感してください。

# 第4部 カーネル編 — スケジューリング

## ⑩ コンテキストスイッチ

### 何が起きているか
CPUコア数は有限(例: 4)なのに、実行可能タスクはそれより多い。
そこでカーネルは短時間ごとにタスクを切り替えます。これが
**コンテキストスイッチ**。1回の切替でカーネルが行う作業:

1. 現タスクのCPUレジスタ(PC, SP, 汎用レジスタ)を `task_struct` に退避
2. 次タスクのレジスタを復元
3. **アドレス空間が変わるなら**ページテーブル(CR3 / TTBR)を切替 →
   **TLB(アドレス変換キャッシュ)がフラッシュ**され、以後しばらく遅くなる
4. カーネルモード↔ユーザモードの遷移

**スレッド間の切替は同じアドレス空間なので TLB フラッシュが不要**で、
プロセス間切替より軽い。これがスレッドが「軽量」な理由の1つです。

### 2種類のスイッチ
| 種類 | 契機 | /proc/<pid>/status |
|------|------|--------------------|
| 自発的 (voluntary) | I/O待ち・`sleep`・ロック待ちで自らCPUを手放す | `voluntary_ctxt_switches` |
| 非自発的 (nonvoluntary) | タイムスライスを使い切り強制的に奪われる | `nonvoluntary_ctxt_switches` |

### 観察
`app/10_context_switch.c`(CPU数と同数以上のスレッドを回す):
```bash
./build/10_context_switch &
PID=$!
grep -i ctxt /proc/$PID/status
# あるいは 1秒ごとの切替回数:
pidstat -w -p $PID 1
```
**コスト感**: 1回の切替は概ね数百ns〜数µs。頻発すると
「計算せず切替ばかり」でスループットが落ちる(スラッシング)。
組み込みのリアルタイム制御では、この揺らぎ(ジッタ)が問題になります。

## ⑪ スケジューラ(CFS / EEVDF)

### なぜこの知識が必要か
「なぜ自分のスレッドが期待通り走らないのか」「優先度をどう付けるか」は
スケジューラを知らないと詰められません。リアルタイム制御では死活問題です。

### CFS の考え方
Linux の通常スケジューラは長らく **CFS (Completely Fair Scheduler)** でした
(カーネル 6.6 以降は後継の **EEVDF** が既定)。CFS の核心:

- 各タスクに **vruntime(仮想実行時間)** を持たせる。走った分だけ増える。
- **常に vruntime が最小のタスク**を次に走らせる → 全員が均等に進む。
- タスクは赤黒木(RB-tree)で vruntime 順に管理され、最小取り出しが O(log n)。
- **nice値**(-20〜+19)で重み付け。nice が低い(優先度高)ほど vruntime の
  増加が緩やかになり、より多くCPUをもらえる。
- タイムスライスは固定ではなく、実行可能タスク数に応じて動的に決まる。

```
実行可能タスク (vruntime順の赤黒木)
        [vr=50]
       /       \
   [vr=30]    [vr=80]
   /
[vr=10] ← 最小。次はこれを走らせる → 走った後 vruntime が増えて木の右へ移動
```

### スケジューリングポリシー(組み込みで重要)
| ポリシー | 用途 |
|----------|------|
| `SCHED_OTHER` (CFS/EEVDF) | 通常タスク。既定 |
| `SCHED_FIFO` | リアルタイム。優先度が高い限り自発的に手放すまで走り続ける |
| `SCHED_RR` | リアルタイム + ラウンドロビン(同優先度で時分割) |
| `SCHED_DEADLINE` | 周期・実行時間・締切を指定する EDF ベース |

制御ループを `SCHED_FIFO` + 高優先度 + `mlockall`(ページアウト防止) +
CPUアフィニティ(`taskset`/`pthread_setaffinity_np`)で特定コアに固定、が
リアルタイム制御の定番構成です。`chrt` コマンドでポリシー確認/設定可能:
```bash
chrt -p <PID>              # 現在のポリシーと優先度
sudo chrt -f 80 ./myctl    # SCHED_FIFO 優先度80 で起動
```

### 観察
```bash
top            # %CPU, PR(優先度), NI(nice)
htop           # 見やすい。F2でカラム追加
ps -eo pid,tid,class,rtprio,ni,psr,comm   # class=ポリシー, psr=実行中コア
```

# 実務ではどう使われるか

- **ROS2**: 各ノードは独立プロセス(隔離)。ノード内の executor が
  コールバックをスレッドで並行実行。DDS通信スレッドも別に回る。
- **Webサーバ/ブローカ**: マスタープロセスが `fork` でワーカー多重化
  (nginx, PostgreSQL)。あるいはスレッドプールで接続を捌く。
- **組み込み制御機**:
  - 制御スレッド: `SCHED_FIFO` 高優先度、周期実行、`mlockall`。
  - 通信スレッド: 通常優先度、ソケットI/Oで自発的スリープ。
  - 監視(watchdog)プロセス: 別プロセスで本体を監視し、落ちたら再起動。
- **デバイスドライバ連携**: ユーザ空間スレッドが `/dev/xxx` を read/ioctl、
  カーネル側はカーネルスレッド(kthread)や割り込みで応答。`driver/driver_stub.c`
  はその「ユーザ空間からデバイスを叩く層」の最小形。
- **デーモン化**: fork して親を殺し孤児化 → systemd 配下の常駐サービスに。

# よくある間違い(総まとめ)

1. **fork 前に stdout を flush しない** → 出力が親子で二重化。
2. **fork の戻り値を分岐しない** → 親子で同じ処理を実行。
3. **wait 忘れ** → ゾンビ蓄積 → PID枯渇。
4. **SIGCHLDハンドラで wait を1回だけ** → 取りこぼし。`while(waitpid(...WNOHANG)>0)`。
5. **exec 後に「戻ってくる前提」のコード** → 成功時は戻らない。
6. **exec の引数末尾 NULL 忘れ**。
7. **pthread のエラーを errno で見る** → pthreadは戻り値。`strerror(rc)`。
8. **共有変数を排他なしで更新** → データ競合(`make race` の通り値が壊れる)。
9. **join も detach もしない** → スレッド資源リーク。
10. **ループ変数のアドレスをスレッド引数に渡す** → 全スレッドが同じ値を見る。
11. **fork したプロセスでmutexを共有できると思う** → プロセス間は別アドレス空間。
    プロセス間排他は `PTHREAD_PROCESS_SHARED` 属性 + 共有メモリ、または名前付きセマフォ。

各問、選択式または短答。解答・解説は末尾。

**Q1.** `fork()` の戻り値について正しいものをすべて選べ。
- (a) 親には子のPIDが返る
- (b) 子には0が返る
- (c) 親子とも同じ値が返る
- (d) 失敗時は-1

- (a) スレッド専用の構造体 thread_struct が別に存在する
- (b) どちらも task_struct で表され、clone() のフラグ(mm等の共有有無)が違うだけ

正しいものは。
- (a) getpid()==gettid()、getpidはカーネルのTGID、gettidはカーネルのpid
- (b) getpid()!=gettid() が常に成り立つ

## 解答・解説

**A1: (a)(b)(d)** — forkは1回の呼び出しで親子2回returnし、親には子PID、
子には0、失敗時-1。(c)は誤り(親子で戻り値が違うからこそ分岐できる)。

**A2: (b)** — Linuxはスレッドも task_struct。`clone()` に `CLONE_VM` 等を
付けるとアドレス空間等を共有する「スレッド」、付けなければ「プロセス」。
これがLinuxのスレッドモデルの本質。

**A3: (b)** — execはプロセスを作らず、アドレス空間を置換。PIDは不変、
成功すれば元コードに戻らない。だから(a)(c)(d)は誤り。

**A4: (b)** — ゾンビ=終了済み・未回収。(a)は孤児の説明。ゾンビはCPUも
メモリもほぼ使わないがPIDを占有する。

**A5: (c)** — 最寄りのsubreaper(なければPID1)。現代のsystemd環境では
ユーザセッションのsystemdがsubreaperになることも多い。

**A6: (c)** — スタックはスレッド固有(+レジスタ, errno, TLS)。
グローバル・ヒープ・FD表は共有。だから排他制御が必要になる。

**A7: (a)** — 生成 fork↔pthread_create、回収 wait↔pthread_join が対応。
未回収の残骸(ゾンビ / 未joinスレッド資源)まで対応関係にある。

**A8: (b)** — 同一アドレス空間なのでページテーブル(CR3/TTBR)切替と
TLBフラッシュが不要。レジスタ退避はスレッドでも必要なので(a)は誤り。
スレッドもカーネルが管理しカーネルモードにも入るので(c)(d)も誤り。

**A9: (b)** — CFSはvruntime最小のタスクを選ぶ。nice値はvruntimeの
増加速度に重みを付ける。赤黒木で最小取り出しがO(log n)。

**A10: (a)** — シングルスレッドでは一致。用語のねじれに注意:
ユーザの"PID"=カーネルTGID、ユーザの"TID"=カーネルpid。
